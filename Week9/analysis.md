## 실행 환경과 측정 범위

측정 환경은 **Python 3.12.14 / Linux x86_64**이다. 이 파일과 CSV·그래프는 이 환경에서 실제 실행한 값으로 생성되며, 다른 환경의 수치와 같다고 가정하지 않는다. 제출자의 Colab에서 전체 실행하면 현재 실행의 측정값으로 다시 생성된다.

- n = 100, 200, 400, 800; 입력은 무작위·정렬·역순·거의 정렬·중복 포함 5종.
- 시드는 2026+n이며, 각 조건에서 세 알고리즘에 같은 원본의 복사본을 전달한다.
- 조건별 1회 워밍업 뒤 5회 측정하고 중앙값을 사용한다. 매 반복마다 알고리즘 실행 순서를 고정 시드로 섞는다.
- time.perf_counter_ns()로 정렬 함수 호출만 측정하며 생성·복사·검증·I/O는 측정 밖에 둔다. 공통 key 함수 호출 비용은 포함된다.
- benchmark.csv는 조건별 요약 60행, benchmark_samples.csv는 개별 측정 300행이며 단위는 모두 ms이다.

## 2. 정렬된 입력에서의 차이

조기 종료 버블은 첫 패스의 n−1번 비교 뒤 교환이 없으면 종료하고, 삽입 정렬은 매 원소마다 바로 멈추므로 둘 다 Θ(n)이다. 선택 정렬은 정렬 여부와 관계없이 n(n−1)/2번 비교하므로 Θ(n²)이다. 정렬 입력의 버블·삽입 시간이 매우 작으면 함수 호출과 타이머·스케줄링 비용의 상대적 비중이 커질 수 있다.

## 3. 안정성과 이동 비용이 중요한 경우

같은 나이의 회원을 가입 순서대로 유지하거나 여러 기준을 순차적으로 정렬할 때 안정성이 중요하다. (2,A), (2,B), (1,C)를 첫 번째 필드만으로 정렬하면 버블·삽입은 A→B를 유지하지만 교환형 선택 정렬은 B→A로 바뀌므로 불안정하다. 크거나 쓰기 비용이 비싼 레코드에서는 비교뿐 아니라 실제 데이터 이동도 중요하며, 선택 정렬의 교환 횟수는 최대 n−1회이다. 단, swap 1회와 shift 1회는 서로 같은 비용 단위가 아니며 원소의 최종 배치 쓰기도 별도이므로 계측 수치만 단순 합산해 우열을 단정하지 않는다.

## 4. 거의 정렬된 입력과 역전쌍

이번 nearly_sorted는 오름차순에서 인접 교환을 max(1,n//20)회 적용한 입력이다. 인접 교환 한 번은 역전쌍을 하나 늘리거나 줄이므로, n=800에서는 역전쌍 수가 최대 40이며 실제 삽입 정렬의 shift는 **36회**, 키 비교는 **835회**였다. 삽입 정렬의 shift 횟수는 역전쌍 수와 같으므로 이 구현은 Θ(n+I)의 비용으로 거의 정렬된 입력에 대응하며, 여기서 I는 초기 역전쌍 수이다. 버블도 적은 인접 교환과 조기 종료의 이점을 얻지만 패스 수는 역전쌍의 개수뿐 아니라 위치에도 영향을 받는다.

## 5. 이론과 실측이 다른 이유

첫째, Big-O와 Θ는 점근적인 증가 차수이므로 key 함수 호출·반복문·대입·분기 등 Python 구현의 상수항과 하위 차수 비용을 직접 나타내지 않는다. 둘째, CPU 캐시·운영체제 스케줄링·백그라운드 작업과 타이머 오차로 같은 코드의 측정값이 변할 수 있다. 워밍업·실행 순서 섞기·반복 중앙값으로 영향을 줄였지만 완전히 없앨 수는 없다.

## 알고리즘 선택 근거

정렬되었거나 역전쌍이 적은 작은 입력에는 삽입 정렬을 우선 고려할 수 있다. 동일 키의 순서가 필요하면 이 구현들 중 버블·삽입을 선택하며, 교환 횟수에 제약이 있으면 선택 정렬의 특성을 고려한다. 이번 측정의 가장 빠른 알고리즘은 위 표에 그대로 제시하며, 그 결과를 모든 데이터·크기·실행 환경에 일반화하지 않는다. 큰 입력에서는 기본 정렬의 최악 Θ(n²) 한계를 고려하여 병합 정렬 등 더 낮은 증가 차수의 알고리즘이 필요하다.
